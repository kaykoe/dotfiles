# Writing Skills

## What a skill is

A skill is a folder containing a `SKILL.md` (YAML frontmatter + Markdown body)
that an agent loads on demand when its `description` matches the current task.
The frontmatter `description` is the *only* thing the agent sees before
deciding to load the skill — everything else is progressive disclosure that
loads only once the skill is triggered.

```
skill-name/
├── SKILL.md           # required: frontmatter + core instructions
├── REFERENCE.md        # optional: detailed docs, loaded only if linked and needed
├── EXAMPLES.md         # optional: worked examples
├── scripts/            # optional: deterministic helper scripts
│   └── helper.py
└── assets/             # optional: templates, schemas, static files
```

Keep references one level deep from SKILL.md (don't chain REFERENCE.md ->
OTHER.md -> ANOTHER.md). The agent should never need more than one hop.

## Process

1. **Gather requirements**
   - What task/domain does the skill cover?
   - What specific triggers (keywords, file types, situations) should invoke it?
   - Does it need deterministic scripts, or is guidance enough?
   - Any reference material (schemas, API docs, examples) to bundle?

2. **Draft the skill**
   - Write frontmatter first (`name`, `description`), then the body.
   - Keep SKILL.md itself short — push detail into linked files.
   - Add scripts only for deterministic, repeatable, or error-prone operations.

3. **Review before shipping** — walk the checklist below.

## Frontmatter requirements

```yaml
---
name: skill-name
description: What it does. Use when [specific, concrete triggers].
---
```

- `name` must be a kebab-case slug and must match the containing directory name.
- `description` is the single most important field:
  - Max ~1024 characters.
  - Third person, factual, no marketing language.
  - Sentence 1: what capability the skill provides.
  - Sentence 2: "Use when ..." with concrete triggers — keywords, file
    extensions, task types, tool names — not vague categories.
  - Must be specific enough that the agent can distinguish this skill from
    other similar skills without opening the file.

**Good:**
```
Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
```

**Bad:**
```
Helps with documents.
```

## Body structure (progressive disclosure)

Order sections so an agent can stop reading as soon as it has enough
information — most-needed material first:

```md
# Skill Name

## Quick start
[Minimal example that solves the common case in a few lines]

## Workflows
[Step-by-step procedures, as numbered lists; include a checklist for
multi-step or high-risk tasks]

## Advanced / edge cases
[Rarely needed detail; link out: see REFERENCE.md]
```

- Prefer imperative, numbered steps over prose paragraphs.
- Prefer tables/checklists over long explanations when checking conditions.
- State assumptions and defaults explicitly instead of asking the user.
- Include at least one concrete, runnable example — abstract description
  alone is not enough for an agent to execute correctly.
- Never include time-sensitive information (dates, "latest version", "as of
  today") since skills are read long after being written.
- Use consistent terminology throughout (don't rename the same concept across
  sections).

## When to add scripts vs. plain instructions

Add a script when:
- The operation is deterministic (validation, formatting, parsing).
- The same code would otherwise be regenerated by the agent every time,
  wasting tokens and risking subtle mistakes.
- Errors need explicit, structured handling (exit codes, JSON error output)
  rather than free-form agent judgment.

Keep it as instructions when:
- The task requires judgment, context-reading, or varies per invocation.
- A one-off shell command already does the job reliably.

Scripts should:
- Be runnable directly (`executable_*` if deployed via chezmoi, or documented
  invocation otherwise).
- Fail loudly with non-zero exit codes and clear stderr messages.
- Avoid hidden network/credential dependencies unless documented in the
  skill body with a preflight check.

## When to split into multiple files

Split content out of SKILL.md when:
- SKILL.md would exceed roughly 100–150 lines.
- Content covers genuinely distinct sub-domains (e.g., schema reference vs.
  usage examples vs. troubleshooting).
- A section is only needed for advanced/rare cases — keep the common path
  fast in SKILL.md and link the rest.

Reference files should be self-contained: an agent following a link should
not need to guess additional context back in SKILL.md.

## Common mistakes to avoid

- Vague description ("helps with X") that doesn't say when to trigger it.
- Burying the quick-start example under long background/motivation prose.
- Duplicating information across SKILL.md and reference files instead of
  linking once.
- Mixing unrelated capabilities into one skill instead of splitting them.
- Embedding secrets, tokens, or machine-specific paths directly in the file.
- Skipping the review/checklist step before considering the skill "done".

## Checklist before shipping a skill

- [ ] `name` in frontmatter matches the directory slug exactly.
- [ ] `description` states capability + concrete "Use when" triggers, ≤ ~1024 chars.
- [ ] SKILL.md body is concise; detail that isn't always needed lives in
      linked files, one hop deep.
- [ ] At least one concrete, working example is included.
- [ ] No time-sensitive or machine-specific information baked in.
- [ ] Terminology is consistent throughout.
- [ ] Scripts (if any) fail loudly and are documented with usage examples.
- [ ] If the skill depends on external services/credentials, document the
      required environment variables/tokens and add a preflight check before
      any API call is attempted.
- [ ] File lives at `<skills-root>/<slug>/SKILL.md` per the host agent's
      expected skill discovery path.
